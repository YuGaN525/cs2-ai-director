# AI导播程序自动检查更新开发说明

日期：2026-11-09，Asia/Shanghai。状态：**新增下一步计划，尚未实现**。配套：[逐项开发步骤 UPD-00～13](自动检查更新开发步骤清单-2026-11-09.md)。

用户要求将程序自动检测最新版本加入下一步开发计划。第一阶段交付“启动后后台检查、定期检查、手动检查、更新提示和前往官网下载”；第二阶段扩展“程序内下载、校验、用户确认后退出替换”。第二阶段单独排期，不把自动安装当作本次用户已要求的默认行为。当前版本仍为1.13.0，本轮只更新计划，不提升版本、不构建或部署。

## 2 产品范围与默认行为

以下为本轮建议的工程默认值，可在UPD-00实施前按真实环境调整；用户已经确认的是新增自动检查功能。

1. 打包GUI默认开启自动检查。首次窗口可交互后延迟10秒，并加入0～20秒抖动；距离上次有效检查不足24小时则使用缓存展示，不重复请求。源码GUI默认不自动访问发行接口，但允许手动检查；训练CLI、worker及普通自检不隐式联网。
2. 常驻GUI每24小时检查一次；休眠恢复或重启只补一次到期检查，不补跑积压次数。手动检查可绕过24小时缓存，但同进程合并在途请求，并限制30秒内重复点击。
3. 默认选择stable；beta须用户明确选择。公测开关不修改账号资格、模型灰度或平台预算。无公测客户端时显示“公测通道暂无发行”，不自动切换stable。
4. 检查无需登录，不发送账号token、Cookie、设备标识、个人API密钥或本地配置。下载公开客户端不等于获得执行资格。
5. 自动发现新版仅显示可关闭的提示条/徽标，不抢焦点、不弹阻塞对话框、不停止导播或训练。设置中的“程序更新”在普通模式可见。
6. 更新详情显示当前版本、目标版本、通道、包大小、更新说明、检查时间与可用操作；更新说明用只读纯文本、局部滚轮上下查看，不执行HTML或远端脚本。
7. 第一阶段提供“前往官网下载”“稍后提醒”“忽略此版本”。仅用户点击时打开受信官网产品页，由用户下载并按说明更新；不自动运行下载的exe。
8. 用户关闭自动检查后，手动按钮仍可用。跳过仅抑制对应目标的自动提醒，设置页仍显示存在更新；目标身份至少包含origin、channel、releaseId、version、hash、revision，后续新版本仍可提醒。
9. 当前1.13.0高于最后记录的stable 1.11.0时，显示“当前版本高于所选通道发行版”，不提示降级、不误报更新成功。

更新检查失败、网站关闭发行服务或断网不改变现有导播执行资格。仍按原账号、设备、签名模型与离线凭据决定能否运行。

## 3 更新来源与接口

### 3.1 第一阶段复用接口

| 接口 | 用法 |
| --- | --- |
| `GET /api/director/client-releases?channel=stable` | 获取所选通道启用的客户端；beta同理。现有实现返回 `ApiResponse<IReadOnlyList<DirectorClientView>>` |
| `GET /api/director/client-releases/{id}/file` | 已有公开文件端点；第一阶段不在程序内调用它下载 |
| `https://www.yuzibei.cn/tools/ai-director` | 用户点击更新后的官网入口；以后若增加通道定位参数，须先由网站实现并测试，不能假设已支持 |

现有单条字段为 `id/version/artifactHash/artifactBytes/notes/enabled/revision/downloadPath/channel`。版本注册只接受三段数字，每段1～4位；当前没有pre-release标签、发布时间、最低系统版本、CPU架构、强制更新标志或客户端发行签名。不能凭字段名称自行假定这些能力已经存在。

查询与页面地址来自有效的固定网站信任配置或构建时受信发行源；不从普通业务响应、用户文本或登录响应学习新域名。配置缺失/无效时显示“更新源未配置/无效”，不偷偷换成任意镜像。GitHub用于源码版本交付，不自动作为官网失败后的可执行文件信任替代源。

### 3.2 协议与选择规则

- 按现有API成功封套解析；在UPD-01提取真实源码契约及匿名样本，不臆造`data`之外的成功字段。补JSON Schema、OpenAPI查询参数与错误样本，两仓逐字节核对。
- 仅接受enabled=true、channel与请求相同、合法UUID、有效三段数字、64位十六进制SHA256、正整数包大小和非负整数revision的记录。bool不作为数字；字段长度及响应大小有界。
- 当前后台策略为每通道最多一条启用记录。0条表示“暂无发行”；多于1条表示发行状态冲突，提示网站核查，不按CreatedAt排序或随便挑一条。
- `revision`是单条记录的CAS修订号，不能当作跨版本全局更新序号。版本大小按数字三元组比较：1.9.0小于1.10.0；若历史有前导零，按数字比较并保留原显示值。
- 同版本新hash不能被当成静默补丁；出现同版本包身份冲突时报告异常。没有记录本机发行hash的源码/旧构建不推测其包身份，只按版本作提示，不自动替换。
- 未知版本格式不做字符串猜测。后续支持beta后缀或其他平台须另行扩展契约；现阶段beta是独立通道，不是版本号后缀。
- 服务端可重启用较低版本，但客户端不自动降级。beta转stable若稳定版更低，保留当前程序并说明；当前服务器同版本跨通道注册会冲突，晋升方案须网站显式设计，不能隐式重复登记。

### 3.3 下载地址与信任

第一阶段只打开构造出的固定官网产品页，不打开服务器notes中的链接，不直接信任downloadPath。若进入程序内下载阶段，必须从已验证id构造同源文件路径，拒绝绝对外站URL、协议降级及越源重定向；重定向必须逐跳校验后才发请求，不能先跟随后检查。

HTTPS发行列表与SHA256能提供现有信任源内的完整性核对，但SHA256本身不是数字签名。第一阶段不宣称具备独立签名更新或抗发行源篡改能力；第二阶段自动替换必须先完成UPD-10的签名、兼容性及回退设计。

## 4 客户端结构与接入点

新增模块名为建议，实施时按仓库结构确定，避免把HTTP与调度塞入导播评分循环。

| 模块 | 职责 |
| --- | --- |
| `client_update.py`（新增） | 无Tk的发行DTO校验、版本比较、目标选择、结果状态；HTTP适配器可注入 |
| `client_update_state.py`（新增或小模块合并） | 缓存、已忽略目标、时间与跨进程检查租约；不含账号凭据 |
| `client_version.py` | 继续作为版本唯一来源；新增构建通道/平台信息时与spec一起固定，不从文件名猜测 |
| `desktop_ui.py` | 更新设置区、说明滚动框和按钮；保持已有主题与可访问性 |
| `desktop_status.py` | 只读取内存中的更新快照，不在每秒状态刷新中联网或访问缓存数据库 |
| `desktop_tasks.py` | 复用结果投递，更新服务自己持有cancel事件与generation；现有Tasks只做到关闭后丢结果，不能当成网络取消 |
| `cs2_ai_director.py`、`trainer_gui.py` | GUI启动/退出、偏好变化与提醒接入；两者共用检查状态 |

更新请求有独立超时、独立并发限制，不占账号续签、模型下载、采集写入和OBS队列。关闭窗口取消后续调度、丢弃迟到结果；不等待无期限网络工作，也不因更新任务阻塞正常关闭保存。

## 5 状态、缓存与调度

### 5.1 明确的界面状态

| 状态 | 展示及行为 |
| --- | --- |
| disabled / not_checked | 自动检查关闭 / 尚未检查；手动检查可用 |
| checking | 正在检查；合并重复请求 |
| up_to_date | 本次有效响应证明版本相同；显示成功检查时间 |
| update_available | 有更高的有效发行版；提供详情及官网按钮 |
| ahead_of_channel | 当前版本高于通道发行版，不降级 |
| no_release | 通道暂无启用发行，不等同“已是最新” |
| source_unconfigured / source_invalid | 无可用受信更新源，继续原业务 |
| check_failed / service_unavailable | 网络、协议或服务错误；保留历史结果并明确“上次结果，未确认当前状态” |

缓存是提示依据，不能替代新鲜的下载授权或签名验证。失败不刷新last_success；旧缓存的“已是最新”不得包装成本次成功。时钟回拨、缓存来源/通道/格式不匹配时使检查时效失效，不能影响许可时钟。

### 5.2 持久化边界

- `preferences.py`新增`auto_check_updates: bool`、`update_channel: stable|beta`；按类型显式扩展校验。默认补值、逐字段更新，保留未知旧键。仅新增可兼容键时不盲目提升`PRAGMA user_version`，否则旧程序会因schema>1拒绝启动。
- 更新缓存独立存储，例如`client-updates.sqlite3`，包含schema_version、origin、channel、最近尝试/成功时间、已验证记录、忽略目标与有限重试状态。它不是账号/模型数据库，也不保存token。
- 导播与训练器同时运行时使用同一短事务租约防重复请求，记录owner、到期与代次；HTTP期间不持有数据库事务。崩溃后有界恢复，时钟异常时不永久阻塞。
- 单次应用中只显示一次同目标自动提醒；跨进程通过共享提醒认领去重。两个界面都可查看同一结果，不能各弹一次模态窗口。

### 5.3 有界网络策略

建议连接超时3秒、读取超时5秒、整次检查总时限10秒、响应体上限256KiB；慢速分片持续到达也必须受总时限约束。默认重试间隔1分钟、5分钟、30分钟，连续失败后6小时，均带小幅抖动；429尊重有界Retry-After。每次只发一次GET，不自动触发账号登录或供应商请求。

自动开关关闭、通道改变、更新源改变、主窗口关闭均递增generation；旧回包不可覆盖新状态。主线程只接收已经校验过的小结果，不在Tk回调里DNS、联网、读大文件或计算整包hash。程序运行中可以检查元数据，提醒保持静默；程序内大文件下载阶段默认等用户选择合适时机。

## 6 第二阶段 程序内下载与退出替换

此阶段为预留扩展，未完成UPD-10～12时，第一阶段仍保持官网下载流程。采用用户确认后更新，不引入静默强制更新。

1. 网站交付独立版本化的客户端更新清单，明确产品、通道、releaseId、version、包hash/bytes、平台/架构、兼容性、元数据序号和有效期。需要签名时使用单独应用更新信任配置/密钥用途与轮换方案，不混用账号或模型签名职责；旧三字段identity-server.json仍兼容。
2. 先定义签名覆盖的规范字节、固定信任根、有效期/时钟异常、回放与合法回退规则，提供正反例。普通远端响应不能自行成为新信任根。安装包Authenticode若采用，另行固定发行身份并验证；不能把PE头检查当签名验证。
3. 受管临时目录以releaseId/hash隔离，流式写`.part`。校验完整长度与SHA256，通过签名/兼容性检查后再转为ready；磁盘不足、取消、异常中断可恢复，缓存不扫描或清理用户其他目录。
4. 续传使用Range及强ETag/If-Range，严格检查206的Content-Range起止与总长；200应重新开始，416须核对总长与完整hash；身份或ETag变化弃用旧partial，不能拼接不同版本。
5. 应用前重新检查发行仍有效及目标身份一致，重新验签/验hash。用户取消、目标被撤下、下载过期或同版本冲突均不替换。
6. 只有导播已停止、同exe的训练GUI/CLI等相关进程退出、采集/时间线可靠刷写、上传在途操作完成或可恢复后才允许替换。无法确认任一进程状态、刷写失败或文件占用时保持原版本，不能强杀训练。
7. 独立更新助手处理固定目标目录内的替换与备份，不接受任意远端命令行，不借管理员权限写任意路径。明确用户安装目录权限、非管理员路径、中文/空格路径和onefile运行特征；权限不足给出手动更新方式。
8. 新进程握手、自检及启动失败回退分别记录。数据库升级必须有兼容计划；不能把旧exe回退等同数据库可回退，也不能恢复旧账号/队列备份抹掉新记录。DPAPI、个人API、模型及待上传数据原地保留。

## 8 验收与交付

详细用例见UPD步骤清单。第一阶段必须覆盖：版本数字比较、stable/beta隔离、当前高于通道、空发行/异常封套、重复启用、无网络/慢响应/超大响应/429/503、开关与缓存、关闭窗口/切通道迟到结果、双进程去重、更新说明长文本、真实exe和官网下载。

程序自动检查失败时导播、训练、账号续签、采集、模型及离线能力保持原有规则。源码/训练CLI/worker不产生额外隐式请求。仅第一阶段通过时，只能标注“自动检查与提醒完成”，不能标注“自动安装完成”。

每次实际程序版本更新，按用户要求完成对应验证、更新版本和开发记录、提交并推送 `YuGaN525/cs2-ai-director`，核验远端commit并提供链接。GitHub源码更新、网站登记发行包、模型发布是不同交付动作；当前计划不自动触发生产部署或模型灰度变化。

## 9 排期关系

UPD-00～09可先开发，加入下一版本候选；它不关闭原OPT/BETA/ADW的游戏、G4、DPI和长稳待办。UPD-10～12为后续可选安装阶段，UPD-13对每个实际交付阶段执行。版本号在候选固化时统一决定，不在规划时虚增版本。
