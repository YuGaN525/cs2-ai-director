## UPD-00 基线与范围冻结

1. 读取当前AGENTS、两端统一进度和实际Git状态，保留原工作区/暂存/用户修改；从当前程序交付工作区继续，不能覆盖回旧1.12快照。
2. 核对`client_version.py`、PyInstaller spec、共享设置/后台任务及匿名发行接口；记录实际源码commit和dirty范围。
3. 固定首期为自动检查、提示、手动检查与前往官网；确认默认stable、自动检查周期和提醒方式采用本轮建议值，产品调整直接更新本清单。
4. 记录关闭自动检查、未登录、有效离线凭据、导播运行与训练运行的原行为，作为回归基线。

交付：基线说明和保护清单。验收：无版本升级、无生产写入；原业务不因规划/初始化产生更新请求。

## UPD-01 固定两端发行契约

1. 网站侧从`DirectorClientReleasesController`、`DirectorClientView`与API封套定义提取准确字段；对齐成功、无发行、通道非法、停服、429/503、撤下和对象缺失。
2. 在现有delivery契约补充非破坏的发行列表schema、channel查询参数及fixtures；若后续签名协议需要新版本，另建update契约，不重写既有签名字节规则。
3. 明确唯一启用记录、数字版本比较、同版本hash冲突、beta转stable与下载路径规则；`revision`不作为全局版本号。
4. 程序与网站分别验证正反例并逐字节对齐；冻结第一阶段可用字段，不提前依赖不存在的兼容性或签名字段。

交付：契约与共享样本。验收：旧网站/旧程序v1兼容，不改变模型/账号接口；列表取首项的隐含假设已消除。

## UPD-02 版本解析与目标决策

1. 编写无网络、无Tk的版本解析与目标选择函数，返回明确状态及只含允许字段的对象。
2. 处理1.9.0→1.10.0、相同版本、当前高于通道、前导零数值相等、非法/过长版本、未知预发行格式。
3. 校验UUID、channel、enabled、bytes/hash/revision；空列表不算最新，多启用记录不自行选最高；同版本不同包不静默更新。
4. 忽略目标按完整发行身份匹配；切通道和新目标不会继承不相关的忽略标记。

交付：`client_update.py`纯逻辑及有意义的决策测试。验收：stable不吸收beta，1.13.0不会被stable 1.11.0提示降级，无未知格式字符串排序。

## UPD-03 受信更新检查客户端

1. 从固定信任配置取得网站origin，只访问发行列表；检查请求不挂账号Authorization、Cookie、设备ID或供应商密钥。
2. 实现连接/读取/总时限和响应字节上限；TLS正常校验，拒绝越源重定向、HTTPS降级与异常内容。
3. 将网络错误、停服、封套错误、版本冲突分别映射状态；对日志和诊断做允许字段输出，不记录完整响应和环境代理凭据。
4. 注入transport/clock/cancel便于验证；检查失败不进入账号退出、模型撤销或离线许可逻辑。

交付：HTTP适配器及本地可控服务测试。验收：慢响应总时间有界、超大正文被拒绝、失败不被显示为“已是最新”。

## UPD-04 偏好与缓存

1. `preferences.py`增加自动开关和stable/beta通道的显式校验，老数据库缺键采用默认值，兼容schema 1和旧客户端读取。
2. 更新缓存采用独立存储，保存尝试/成功时间、origin/channel、发行身份、忽略目标与缓存版本。
3. 明确失效规则：断网展示带时间的历史结果；失败不推进last_success；通道/源变化、时钟异常和坏缓存触发安全重新检查。
4. 逐字段事务更新与跨进程共享；损坏更新缓存可重建，不能碰账号/模型/采集数据库。缓存清理仅限受管目录。

交付：偏好迁移与缓存读写。验收：老偏好和用户主题不丢失，关闭自动检查重启后保持，手动检查仍可用。

## UPD-05 自动调度与并发

1. GUI可交互后延迟调度，按24小时到期与有限退避执行；源码模式默认关闭自动任务，休眠/重启不追补风暴。
2. 手动按钮合并在途请求并有30秒冷却；切通道、关闭检查、退出时增加generation并取消后续动作。
3. 导播和训练器共用跨进程短租约及缓存；网络执行不持数据库锁，崩溃后有界接管。
4. 主线程接收一次已校验结果；状态每秒刷新不再重复查网/读库。双进程只认领一次同目标提醒。

交付：检查服务与生命周期接口。验收：两窗口同时打开只有一次到期请求；旧通道回包、关闭后的回包不写入新界面；停止和退出不被检查阻塞。

## UPD-06 程序更新界面

1. 在共享设置中新增“程序更新”，显示当前版本、通道、自动检查开关、检查时间和手动按钮；普通模式可见。
2. 主窗口使用非模态更新提示；自动检查失败不连续弹窗，手动检查反馈准确。
3. 详情纯文本滚动，提供前往官网、稍后提醒、忽略此版本；已忽略状态仍可在设置中查看。
4. 官网链接只由固定origin和路径构造；不执行notes中的HTML/命令或任意外链。

交付：共享UI与状态展示。验收：深浅主题、长说明、键盘焦点和滚轮正常；导播/训练不中断、不抢焦点。

## UPD-07 应用装配与关闭

1. 在主GUI和训练GUI接入同一检查服务；沿用单一VERSION，启动不导入额外重型训练依赖。
2. 区分frozen/source/训练CLI/worker模式，不在既有`--check-report`中隐式联网；如新增`--check-updates`，明确为用户主动的联网命令并记录退出码。
3. 关闭时撤销调度、取消请求、抑制迟到提醒；原时间线/数据刷写逻辑保持优先。
4. 状态诊断仅导出版本、通道、结果代码、时间及发行ID，不携带token/私有路径/完整远端错误正文。

交付：主入口、训练器及spec接入。验收：同exe各入口正常，离线导播资格不因更新失败变化，训练子进程不重复提示。

## UPD-08 回归矩阵

| 类别 | 必测场景 | 预期结果 |
| --- | --- | --- |
| 版本 | 高/同/低版本、1.9/1.10、非法格式、同版换hash | 正确状态；无降级、无静默同版替换 |
| 通道 | stable/beta、空通道、重复启用、检查中切换 | 隔离、明确无发行/冲突、旧响应失效 |
| 网络 | 离线、DNS/TLS失败、超时、慢流、超大正文、429/503 | 有界停止与退避，不影响原执行门 |
| 来源 | 外站/降级重定向、无效信任配置、恶意说明 | 拒绝访问非授权源；纯文本展示 |
| 缓存 | 关闭自动、忽略目标、过期/坏缓存、时钟回拨 | 偏好保留、状态诚实、不会永久不再检查 |
| 并发 | 双GUI、重复点击、崩溃租约、关闭窗口 | 单次检查、可恢复、无迟到UI更新 |
| 使用中 | 导播/训练/上传并发、长说明、小窗口 | 无卡顿、无模态抢焦点、无业务配置变化 |
| 兼容 | 旧偏好、源码/CLI/worker、旧客户端发行API | 兼容且无新增隐式网络 |

交付：定向测试、完整程序回归、契约一致性及UI检查。验收：记录真实耗时与失败，不用合成接口冒充生产联调；本项不替代原G4/长稳。

## UPD-09 实际exe第一阶段验收

1. 在隔离输出目录构建候选，固定版本/来源/依赖/公开信任摘要，确保不含测试源或私钥。
2. 用受控测试源验证“发现更高版本、无更新、断网、beta无发行”，在实际exe同时打开导播/训练器核对去重与不打断运行。
3. 对正式官网只读核验发行与受信页面可达；若当前通道确实没有更高版本，记录相应真实状态，不能临时扩大生产公测制造演示。
4. 用户点击前往官网，核对产品页、选择通道和下载包信息；首期不自动运行或替换exe。

交付：候选hash、截图、请求/状态证据与限制。验收：可宣布“自动检查和提醒完成”，不宣布“自动安装完成”。

## UPD-10 第二阶段签名与兼容性前置

1. 两端定义版本化更新清单、产品/通道/平台、兼容性、大小/hash、序号、有效期、签名及撤回规则。
2. 固定独立应用更新信任配置和轮换流程，保留旧identity配置兼容；定义规范字节与未知key/过期/回放的拒绝样本。
3. 明确beta晋升、合法回退、元数据过期及网络不可达时的应用策略；不要以“更高revision”放行任意程序。
4. 明确运行目录权限、便携onefile形式及本地数据库兼容性；需要Authenticode时核验发行身份和签名覆盖。

交付：已对齐的可信更新协议、威胁/故障边界与测试样本。验收：此项未通过不得进入自动替换。

## UPD-11 程序内下载

1. 只允许用户发起；按releaseId/hash建立受管partial目录，检查可用空间并流式下载。
2. 严格校验同源、Range/ETag/Content-Range，覆盖200/206/416及中途换包，不能错误追加。
3. 完成后核验bytes、SHA256、签名与平台兼容；失败保留清晰状态，删除只限本次受管坏包。
4. 应用前重新核对发行是否撤下，处理取消、重启续传及多个窗口争抢。

交付：下载状态机及实际文件故障验证。验收：截断/篡改/撤下/过期/错架构均不能变为ready。

## UPD-12 用户确认后的退出替换

1. 枚举并确认本产品相关进程/执行锁，先安全停止导播、等待训练及数据可靠保存；占用或保存失败时阻止替换。
2. 独立助手限定目标目录、包身份与一次性更新任务，不接受任意命令/路径；不静默提权或强杀进程。
3. 备份原exe，替换后启动并等待新进程握手；失败按明确数据库兼容策略回退，原数据和凭据不回滚覆盖。
4. 验证中文/空格路径、无写权限、磁盘不足、文件占用、安全软件拦截、断电阶段恢复、多进程与新程序失败。

交付：助手、事务状态记录、故障/回退报告。验收：正常升级与所有失败路径均可恢复；不丢训练记录、不替用户扩大资格。

## UPD-13 每次版本交付

1. 根据实际完成阶段决定候选版本；更新`client_version.py`、构建元数据、开发日志与验收状态，保留原待办。
2. 执行相应程序/契约/实际exe检查；记录commit、包大小/hash、通道与依赖。文档规划本身不增加版本号。
3. **每次程序版本更新均提交并推送GitHub程序仓库**，核验远端commit，向用户提供提交链接及测试结果；不等所有长期专项结束才上传已验证的候选更新。
4. 网站侧按实际发行范围登记同一包、核对渠道与下载摘要；程序源码push不等于官网包已启用，不自动发布模型或更新运行中的worker。
5. 同步两端进度，写明检查/下载/安装三个阶段各自完成情况与回退方式。

交付：GitHub提交链接、版本与包摘要、验证记录、剩余清单。验收：版本、源码、官网包身份可相互追溯，无“代码已推送但更新源未登记却声称用户已可更新”的误报。

## 点对点执行口令

- “完成UPD-00～02”：固定现状和两端契约，完成版本判断。
- “完成UPD-03～07”：完成检查服务、缓存、调度与界面接入。
- “完成UPD-08～09及13”：验证首期实际exe并提交GitHub；官网包启用按实际发行指令办理。
- “开发程序内下载与退出更新”：进入UPD-10～12，依次完成签名/兼容、下载、替换回退，再执行13。

每项结束报告：改动内容、文件/commit、输入输出示例、已执行测试、证据位置、未满足条件和下一依赖。仅计划完成时不得给实现项勾选完成。
